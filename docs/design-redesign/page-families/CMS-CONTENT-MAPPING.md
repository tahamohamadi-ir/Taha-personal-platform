# CMS and admin-panel content mapping

Status: **functional specification / implementation not included**  
Principle: CMS controls content and editorial selection; the Design System
controls visual language and accessibility behavior.

## Governance boundary

### Editors may manage

- locale-specific titles, summaries, body blocks, metadata, SEO, slugs, and
  publication state;
- section visibility and order within an approved template;
- featured records and optional start/end windows;
- preview media, galleries, captions, alt text, focal point, credits, licence,
  and download visibility;
- taxonomies, series, collections, tags, and manually curated relationships;
- Home CTA labels and route-picker destinations from an allowlisted route set;
- graph nodes/edges and timeline records;
- contact availability, approved academic email, approved social profiles,
  form enablement, attachment policy, FAQ, and response-expectation copy;
- per-locale canonical content readiness and alternate-locale publication.

### Locked in code/design tokens

- color roles, typography families/scales, spacing, radii, borders, shadows,
  glass opacity, grid, breakpoints, and motion limits;
- component anatomy, allowed variants, accessible names, focus behavior,
  error patterns, heading rules, and reading measure;
- arbitrary CSS, HTML, JavaScript, tracking snippets, remote embeds, and custom
  script injection;
- core header/footer structure, privacy disclosures, route families, and
  canonical/alternate-locale logic.

An editor may select a safe component variant; an editor may not restyle the
variant.

## Shared record fields

Every public record uses a common publishing envelope:

| Field | Required | Notes |
|---|---:|---|
| Stable ID | Yes | Immutable internal identifier |
| Locale | Yes | English and Persian are separate records/states |
| Title | Yes | Plain text with validated length |
| Slug | Yes | Unique within locale and route family |
| Summary | Yes for index | Short approved preview; never generated by frontend |
| Body | Detail gate | Structured portable rich text/block content |
| Publication state | Yes | Draft, review, scheduled, published, archived |
| Publish/unpublish time | Optional | Server-authoritative schedule |
| SEO title/description | Optional | Fallbacks are deterministic and non-inventive |
| Social image | Optional | Rights, crop, alt, and locale metadata required |
| Canonical family | Yes | Chosen from route allowlist |
| Translation relationship | Optional | Links records without forcing simultaneous publication |
| Featured state/window | Optional | Separate from publication state |
| Sort priority | Optional | Tie-breaker after editorial/date rules |
| Privacy review | Sensitive families | Required for work/project/contact records |
| Revision/audit metadata | Yes | Actor, time, summary, previous version pointer |

## Visual-slot mapping

| Visual slot | CMS source | Selection/order | Publication rule | Locked behavior |
|---|---|---|---|---|
| Header navigation | Navigation config with route picker | Fixed primary slots; optional child links | Destination must be public in locale | Geometry, responsive menu, focus order |
| Home sections | Home composition record | Approved section IDs, visibility, order | Hidden section produces no empty gap | Section templates and spacing |
| Home selected work | Curated relationship | Manual selection plus optional window | Target record must be published/sanitized | Max visible count and component variant |
| Home graph | Graph dataset | Node/edge order and positions | Only visible published nodes/relationships | 2D/list fallback, 3D progressive enhancement |
| Home journey | Timeline dataset | Manual sequence | Each item needs approved label/summary | Timeline geometry and responsive conversion |

| Filters | Taxonomy configuration | Admin order of allowlisted facets | Only facets with published records appear | Control types, URL behavior, labels |

## Family-specific data

### Writing

- kind: essay, note, memory, society, or another administrator-defined safe
  taxonomy value;
- series, topics, cover, excerpt, body, authoring date, revised date, feed
  inclusion, rights note, related writing;
- no automatic relationship to projects;
- no likes, views, popularity score, or engagement-rank field in public UI.

### Learning

- kind, objectives, prerequisites, level, format, estimated duration when
  author-approved, lessons/steps, resources, references, downloadable files;
- learning-path order is editorial, not visitor progress;
- certification/completion UI is absent unless a separately approved product
  scope introduces real behavior.

### Projects and evidence records

- type, topics, safe title/summary/body, contribution, methods, artifacts,
  limitations, confidentiality/sanitization statement, case-study visibility;
- separate private source fields from public projections;
- code, demo, dataset, documentation, and download each have explicit
  unavailable/private/request/public states;
- an approval checklist blocks publication when sensitive fields/media remain.

### Research and publications

- research directions, questions, methods, impact framing, related records;
- publication type, title, authors, venue, date, status, identifiers, abstract,
  files, citation formats, rights;
- metadata fields publish only when verified; blank values stay absent;
- publications have independent canonical detail routes while remaining a
  child destination under Research navigation.

### Creative work

- medium, year, role, context, statement, ordered media, captions, process,
  credits, licence, alt text, related creative records;
- lead focal point and detail/list crops are stored separately where needed;
- visual-work publication requires media-rights and accessibility review.

### About, CV, and timeline

- profile statements, principles, skills taxonomy, languages, interests;
- typed experience, education, research, publication, certificate, award, and
  other approved record families remain separate;
- each record has preview and detail visibility; detail is not created unless
  the eligibility gate passes;
- CV/document records keep original owner-supplied files, locale, type,
  effective date, display label, and visibility. The CMS does not regenerate or
  rename source documents.

### Contact

- approved academic email, approved profile links, availability text, purpose
  choices, FAQ, form enabled state, attachment enabled state/limits, recipient
  routing alias, spam controls, and privacy text;
- phone and personal mail fields do not exist in the public schema;
- messages are delivered by the configured backend transport and are not
  persisted in the website content database;
- operational delivery logs must avoid message body and sensitive form data;
  retention, access, and deletion follow deployment policy;
- success is shown only after confirmed transport acceptance; failure retains
  the user's form values and offers retry/approved alternate contact.

## Graph editor functional specification

### Phase 1 — 2D authoring and 2D public output

Admin features:

1. create, rename, duplicate, group, hide, archive, and delete-with-confirmation
   nodes;
2. connect/disconnect nodes and set relation type, direction, weight, and
   localized explanation;
3. drag positioning, snap/grid option, pan, zoom, fit-to-view, minimap, undo,
   redo, keyboard nudging, multi-select, and alignment/distribution;
4. per-locale label, short description, accessible label, and linked records;
5. node type/icon/color-role selection from a locked allowlist;
6. validation for orphan nodes, duplicate edges, missing locale labels, broken
   record links, inaccessible labels, and graph cycles only when a selected
   relation type forbids them;
7. draft preview in both locales and both themes;
8. version history, named snapshots, compare, restore, and publish approval;
9. import/export of a versioned JSON graph payload with schema validation;
10. public 2D preview and semantic-list preview before publication.

The public payload contains only published nodes, edges, and linked public
record identifiers. Private notes and admin coordinates are never exposed when
they are not required for rendering.

### Phase 2 — shared-data 3D preview/output

- Admin adds a 3D preview tab using the same payload and optional 3D coordinates
  derived from 2D positions plus editable depth/layer values.
- Editors can tune camera preset, focus target, orbit boundary, label density,
  and glow intensity within locked safe ranges.
- Public runtime selects 3D only when supported and permitted; 2D/list remains
  authoritative for navigation and accessibility.
- Publishing validates that every 3D node maps to a 2D/list node and that no
  relationship exists only in the decorative representation.

## Home composition and editorial selection

The Home composer exposes a fixed catalog of section modules:

- identity lead;
- graph/relationship preview;
- research fit;
- interdisciplinary journey;
- selected projects;
- selected publications;
- Gallery, Writing, and Learning previews;
- collaboration/CV/contact close.

Editors may toggle and reorder modules inside policy constraints, select
records, set display density from approved variants, and set locale copy. The
system prevents removal of the identity lead, use of more than one primary CTA
per viewport, duplicate record selection in the same module, and links to
unpublished targets.

## Media library requirements

- original upload plus derived formats; never overwrite the original;
- MIME/type validation, dimension and size limits, malware scanning where
  relevant, rights/source note, licence, credit, locale caption, alt text,
  focal point, crop previews, decorative flag, and usage references;
- prevent deletion while referenced; allow replace-with-version;
- responsive rendition status and failed-processing recovery;
- SVG uploads are sanitized; arbitrary scripts and external references are
  rejected;
- generated art is labelled as generated concept/illustration where required
  by the publishing policy.

## Workflow, roles, and audit

Recommended roles:

- Owner: full settings, publication, privacy approval, and design-variant
  allowlist management;
- Editor: draft/edit/curate content and media;
- Reviewer: comment, approve, request revision, compare versions;
- Publisher: schedule/publish/unpublish approved records;
- Media manager: assets, rights, alt/caption completeness;
- Viewer/auditor: read-only history and configuration.

Required workflow:

1. draft;
2. content review;
3. locale review;
4. privacy/rights review when applicable;
5. preview against Light/Dark and desktop/mobile/RTL representatives;
6. publish or schedule;
7. invalidate/rebuild affected public pages;
8. retain audit event and rollback pointer.

Bulk actions must show exact affected records and locales before execution.
Destructive actions require confirmation and recoverable archival where
practical.

## Future white-label productization

The personal platform can later become a separately configured product without
allowing content editors to break the system:

- tenant/site profile stores owner identity, approved mark, domain, locales,
  contact policy, route-label vocabulary, and enabled modules;
- brand theme selects from versioned token packs with contrast validation;
- template/module catalog remains shared and versioned;
- content, media, graph, navigation, SEO, and documents are tenant-scoped;
- export/import uses a versioned portable content package without secrets;
- migrations upgrade schema and token-pack versions independently;
- per-tenant custom code is prohibited; extension points are typed blocks,
  route pickers, webhooks, and approved integrations;
- a tenant clone never copies private drafts, contact messages, credentials,
  analytics identifiers, or deployment secrets.

This future mode is a post-project architecture option, not authorization to
change the current route, tenancy, or deployment model.

## Validation gates

Before a public record or composition publishes, validate:

- required locale fields and slug uniqueness;
- canonical/alternate-locale consistency;
- target route publication;
- heading order and safe rich-text blocks;
- media rights, alt/caption, focal point, and processing state;
- privacy/sanitization state for work/contact records;
- no prohibited public contact field;
- relationship integrity and no unpublished target leakage;
- SEO length/preview and social-image readiness;
- Light/Dark and representative RTL/mobile preview;
- audit actor, approval, and rollback reference.
