# R0.1 — طراحی حاکمیت اجرای OpenCode Go

**وضعیت:** تأییدشده برای بازبینی مالک؛ هنوز تصمیم عبور از دروازه نیست  
**تاریخ:** ۱۴ اوت ۲۰۲۶  
**دامنه:** فقط اسناد و شواهد کنترلی R0.1 در P0-G0

## نتیجهٔ مورد انتظار

یک مسیر قابل‌کنترل برای استفاده از عامل‌های OpenCode Go ایجاد شود که در آن
Codex نقش مدیر و بازبین را دارد و عامل‌های OpenCode فقط کارهای مشخص و کم‌خطر
را انجام می‌دهند. نخستین برش، وضعیت اسناد و تصمیم‌های لازم برای R0 را روشن
می‌کند؛ هیچ برنامه، وابستگی، زیرساخت یا استقرار جدیدی نمی‌سازد.

## مرزهای ثابت

- پروژه در P0-G0 باقی می‌ماند. تا وقتی Task Spec کامل و تصمیم صریح مالک وجود
  ندارد، ساخت Astro/Django، وابستگی، API، مدل/اسکیما، Compose/Docker، VPS، DNS
  و deploy ممنوع است.
- مسیرهای قطعی پروژه `apps/web/`، `apps/cms/`، `infra/`، `docs/` و `.github/`
  هستند. R0.1 فقط در `docs/` کار می‌کند.
- دروازهٔ زبان عمومی تغییر نمی‌کند: `/` انتخاب زبان است و `/fa/` و `/en/` ریشه‌های
  مستقل زبان‌اند. R0.1 هیچ route یا محتوایی ایجاد نمی‌کند.
- محتوای فارسی و انگلیسی مستقل‌اند؛ هیچ محتوا، ترجمه، مدل، endpoint، مقدار راز
  یا معیار تازه‌ای حدس زده نمی‌شود.
- هر اقدام واقعی باید در `docs/status/WORK_LOG.md` ثبت شود. هر اعتبارسنجیِ به
  تعویق‌افتاده، شناسهٔ یکتا در `docs/status/deferred-validation.md` می‌گیرد.
  آیتم‌های Critical، High و حداقل گیت انتشار قابل تعویق نیستند.

## برش R0.1

### در دامنه

1. هم‌راستاسازی و استخراج اختلاف میان `PROJECT_MANIFEST.md`، سیاست انتشار،
   سیاست مستندسازی، ADRهای مرتبط و Task List موجود.
2. تهیهٔ Task Spec دقیق برای یک تغییر مستندیِ بعدی که فقط با اسناد مالکیت‌دار
   سروکار دارد.
3. ثبت شواهد، پرسش‌های تصمیم‌گیری و ریسک‌ها در دفاتر رسمی، بدون تغییر در
   آیتم‌های کثیف و بدون‌مالک فعلی.
4. اعتبارسنجی مکانیکی اسناد تغییرکرده و بازبینی مستقلِ تغییرات توسط عامل
   read-only.

### خارج از دامنه

- هرگونه bootstrap، کدنویسی محصول، dependency install یا تغییر application.
- تماس با VPS، DNS، سرویس تولید، Docker/Compose یا پیکربندی استقرار.
- ساخت یا بازنویسی Task List موجود تا وقتی مالکیت آن در Task Spec تعیین نشده است.
- استفاده از credential یا endpoint مسیر‌دهندهٔ خارجی تا بسته‌شدن ریسک مربوطه.

## نقش‌ها و سطح دسترسی

| نقش | وظیفه | مجوزها | مدل پیشنهادی |
| --- | --- | --- | --- |
| Codex (مدیر) | تعیین scope، بررسی قراردادها، review نهایی، staging/commit/push | ابزار محلی فقط برای شواهد و Git؛ بدون نوشتن کد محصول | تصمیم انسانی/بازبینی |
| `r0-scout` | فهرست‌برداری از قراردادها و اختلاف‌ها | read، glob، grep؛ بدون edit، bash یا Git write | مدل سبک مانند DeepSeek V4 Flash یا MiMo V2.5 |
| `r0-docs-executor` | اعمال یک Task Spec مستندیِ تأییدشده | read، glob، grep، edit، todowrite؛ بدون Git write و بدون shell | Kimi K2.7 Code یا GLM-5.2 |
| `r0-verifier` | بررسی مستقل scope، لینک‌ها و ناسازگاری‌ها | read، glob، grep؛ بدون edit، bash یا Git write | GPT-5.6 Luna یا GLM-5.3 |

مدل قوی‌تر برای طراحی، ریسک و بازبینی تخصیص می‌یابد؛ مدل سبک فقط برای
inventory و کنترل‌های مکانیکی به‌کار می‌رود. هر فراخوانی باید نام مدل، scope،
فایل‌های مجاز، نتیجهٔ مورد انتظار و ممنوعیت رازها را صریح داشته باشد.

## جریان کنترل

```text
Codex: قراردادها و Task Spec را بررسی می‌کند
  -> Scout: فقط واقعیت‌ها و اختلاف‌های مستند را گزارش می‌دهد
  -> Codex: گزارش را با قراردادها تطبیق می‌دهد و scope قابل‌نوشتن را تعیین می‌کند
  -> Docs executor: فقط فایل‌های مجاز Task Spec را تغییر می‌دهد
  -> Verifier: diff و معیارهای پذیرش را مستقل بررسی می‌کند
  -> Codex: کنترل نهایی، ثبت ledger، stage انتخابی، commit و push مجاز را انجام می‌دهد
```

عامل اجرایی هرگز commit، push، تغییر پیکربندی مدل/route، ثبت راز یا گسترش
خودسرانهٔ scope انجام نمی‌دهد. اگر Task Spec ناقص باشد، عامل فقط نقص را گزارش
می‌کند و متوقف می‌شود.

## مدیریت session، هزینه و خطا

- هر Task Spec یک نام کوتاه، خروجی قابل‌بررسی، فایل‌های مجاز و معیار پذیرش
  دارد. sessionها برای یک برش مستقل نگه‌داری می‌شوند و برای scope جدید دوباره
  استفاده نمی‌شوند.
- هر مرحله فقط پس از خلاصهٔ کوتاه نتیجهٔ مرحلهٔ قبل فعال می‌شود. این کار هم
  هزینه و هم انتقال فرض‌های بررسی‌نشده را محدود می‌کند.
- timeout، خروجی مبهم یا ادعای فاقد شاهد، «ناموفق» محسوب می‌شود؛ Codex با
  شواهد محلی آن را بازبینی می‌کند یا کار را به عامل بازمی‌گرداند.
- اگر اجرای عامل تغییر خارج از Task Spec بسازد، تغییرات آن stage نمی‌شود و
  موضوع برای تصمیم مالک ثبت می‌گردد. پاک‌سازی مخرب انجام نمی‌شود.
- گزارش هر اجرا فقط شناسهٔ task/session، مدل، فایل‌های بررسی‌شده، نتیجه و شواهد
  غیرحساس را نگه می‌دارد. prompt، لاگ و commit نباید credential داشته باشند.

## 9Router و رازها

یک credential مسیر‌دهنده در گفتگو افشا شده و با `RISK-0008` ثبت شده است. تا
وقتی مالک credential را revoke/rotate نکرده و مسیر جایگزین امن را تأیید نکرده
است، 9Router از پیکربندی و فراخوانی عامل‌ها حذف می‌ماند. راز افشاشده در این
سند، log، commit یا خروجی تکرار نمی‌شود. OpenCode Go که credential معتبرِ مستقل
دارد، تنها provider مجاز این برش است.

## ورودی‌های لازم برای عبور از R0

R0.1 فقط شواهد را آماده می‌کند. تصمیم‌های زیر باید پیش از عبور P0-G0 روشن و در
Task Spec/ADR ثبت شوند:

1. پذیرش استثنای static-only برای RISK-0003 یا اجرای import آزمایشی PostgreSQL
   ایزوله؛ مورد High با تعویق ساده بسته نمی‌شود.
2. بستهٔ محتوای تأییدشدهٔ دو‌زبانه و دارایی‌های مجاز، یا تعیین روشنِ اینکه
   عرضهٔ نخست بدون آن ممکن نیست.
3. انجماد انتخاب‌های فنی و تأیید ADRهای لازم.
4. تصمیم صریح مالک برای عبور یا ماندن در P0-G0.

## معیار پذیرش R0.1

- Task Spec بعدی فقط تغییرهای مجاز، مالکیت فایل‌ها، خروجی، گیت‌ها و fallback را
  به‌صورت قابل‌تست نام می‌برد.
- هیچ فایل خارج از `docs/`، package manifest، dependency lock، کد محصول یا
  پیکربندی deploy ایجاد/تغییر نمی‌شود.
- ادعاهای گزارش Scout و Verifier به فایل و بخش مشخص قرارداد وصل‌اند؛ حدس به
  عنوان واقعیت پذیرفته نمی‌شود.
- هر ریسک یا defer جدید دارای شناسه، مالک، شدت، هدف، mitigation/fallback و
  شاهد است؛ مورد High/Critical به‌عنوان defer بسته نمی‌شود.
- پیش از commit، Codex diff محدود، `git diff --check` و فایل‌های staged را
  بررسی می‌کند. فقط فایل‌های متعلق به همان Task Spec stage می‌شوند.

## بررسی این طراحی

این سند با قراردادهای P0-G0، Manifest پروژه، سیاست انتشار، سیاست مستندسازی،
ADRهای مربوط و Task List موجود هم‌راستا نوشته شده است. تغییر وضعیت دروازه یا
اجرای کار بعدی منوط به بازبینی و تأیید صریح مالک است.
